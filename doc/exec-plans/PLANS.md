# Project Raidline ExecPlan 规范

ExecPlan 是跨阶段工作的活文档，不是一次性待办清单。它让后续 Codex 在缺少聊天历史时仍能从仓库证据继续工作。

## 必须建立计划的情况

- 跨越多个核心类或系统。
- 改变所有权模型、数据迁移或持久化格式。
- 新增 Raid 生命周期、多容器转移、保存/加载。
- 重大重构或需要多个独立实现阶段。
- 无法在一个短任务中可靠实现、验证和关闭。

小型单文件修复可直接使用 `$raidline-feature-delivery`，无需机械创建计划。

## 生命周期

1. 在 `doc/exec-plans/active/` 创建描述性、稳定文件名的 Markdown。
2. 基于当前源码、测试、CMake 和 Git 写现状；不要只复制需求。
3. 实施中持续更新进度、发现、决策、验证和偏差，并保留日期/commit 证据。
4. 未完成时保留在 `active/`，明确下一安全步骤。
5. 玩家结果、自动测试、人工验收、文档和教学交接全部完成后，移动到 `completed/`；保留真实偏差，不重写成理想计划。

## 必需结构

每份计划至少包含：

1. 标题、状态、负责人/工作流和最后更新时间。
2. 目标与玩家可感知结果。
3. 当前仓库状态和可核验基线。
4. 范围与明确不做事项。
5. 主要类型、调用路径与所有权。
6. 必须维持或新增的不变量。
7. 分阶段实现步骤；每阶段有可观察退出条件。
8. 自动测试矩阵、构建/CI 与人工验收。
9. 风险、替代方案与回滚/失败语义。
10. 进度记录、发现记录和决策日志。
11. 最终结果、验证证据、偏差和遗留问题。

## 写作规则

- 使用仓库相对路径、类型和符号，使计划可执行。
- 把事实、决定、假设和候选方案明确分开。
- 不把“运行测试”写成无命令的泛化步骤；链接 `doc/engineering/BUILD_AND_TEST.md` 并列目标测试。
- 不把人工清单写成自动 PASS。
- 不重复整份架构或不变量；链接唯一事实来源，只记录本计划新增或受影响部分。
- 任何范围增加、所有权改变或兼容性决定都进入决策日志。

## 状态约定

- `Draft`：正在形成事实和契约，禁止实现高风险部分。
- `Ready`：契约、阶段和验证标准已明确，可以实施。
- `In Progress`：已开始业务改动，持续记录证据。
- `Blocked`：有明确外部阻塞和已尝试路径。
- `Completed`：Definition of Done 已满足并移入 `completed/`。
