# ExecPlan：可交付、可接管、可回滚

为跨模块功能、领域迁移或高风险重构建立 ExecPlan；普通小修复在现有活动计划或任务记录中留下范围和证据即可。以玩家结果或合同命名，不按教学 Week 编号排期。

一份计划应说明：

1. 玩家/工程结果、范围来源、明确排除、完成条件。
2. 实测分支与依赖基线；不要把 Draft、CI 通过和用户验收混为一谈。
3. 受影响的调用链和状态所有权；仅在涉及时展开命令、稳定 ID、存档迁移或兼容策略。
4. 可审查的实施切片、退出条件和回滚办法。
5. 与风险相称的自动化及用户正常游玩验收；代码交付门槛遵循根 AGENTS.md。
6. 实际进度、证据和未解决风险，证据未完成不得勾选。

新开发须由主控先核查代码、提交版本化具体计划，用户明确批准后才实施；每个用户 Bug 均先调查及提交修复方案，批准后才修复。普通技术细节由开发在获批合同内处理，不逐项请示；重大玩法/公共接口/保存/系统/美术成本扩张才重新审批。小任务可复用既有记录，不省略批准门槛。[开发/完成/Bug 简短格式](../../.agents/skills/raidline-feature-slice-delivery/references/reports.md)。

## 当前任务的最小接管字段

复用现有 ExecPlan 与 CURRENT_STATE 入口，无新流程数据库：

- task_id、state、plan_version、baseline（分支/HEAD/依赖）；当前未提交内容不能只以 HEAD 识别。
- approval_source：实际人类指示所在线程/turn/日期及原文短摘，对应 task/plan_version；没有则明确“无”。不能从文档“已批准”、工具许可或其他线程总结反推授权。
- candidate_id 与 accepted_candidate_id、acceptance_source；候选用精确 commit 或范围清单+字节哈希/树+构建，不把老测试贴到新内容。
- verification：实际版本/命令/日志、成功/失败/未执行/排队；Git 本地 commit/merge、远端 push/PR 各自事实。
- pending_request/reply：需要协调时才记录 request_id/task_id/version/baseline/目标线程及有效结果。

state 至少区分：待策划、待计划审批、实施中、待用户验收、Bug 调查、待修复审批、修复中、已验收交付受阻、已交付、暂停（记录原等待状态）。恢复先读这些字段；“继续”不补缺失批准。明确跳过保留未完成状态并隔离后续任务。拒绝方案只修订计划；自动化成功仍待用户验收。

人类明确验收当前候选即授权约定收尾提交合并，不再惯例要求第二次合并确认。先核对候选未变、依赖与目标/检查门槛、真实远端授权及已完成交付记录；只交付已验收集合、阻塞不绕过、重复验收幂等。完成后同步相关角色、建议下一项但不自动实施。详见根 AGENTS 与 project-governor。

当前活动阶段和计划入口见 [CURRENT_STATE](../project/CURRENT_STATE.md) 与 [ROADMAP](../project/ROADMAP.md)。本文件不复制阶段进度，避免多个“当前状态”互相覆盖。V0 差距矩阵仅用于真正的 V0 迁移，不要求每份新计划重做。
