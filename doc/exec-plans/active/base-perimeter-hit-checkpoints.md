日期：2026-09-09。状态：实现与本地自动化完成，待精确提交 CI 和用户正常游玩验收。

## 复现与根因

同一无窗口真实会话路径、真实临时 SaveRepository：普通命中中位数 29.23 ms、击杀 29.57 ms；
无存储时约 0.22/0.19 ms。Profile 保存中序列化约 3 ms，回读校验/备份/原子替换约 25 ms。
Daily 每次 HP 变化都同步 commitProfileCandidate；不是重新生成地图。
旧 Raid 回归没有配置真实存储，也没有要求实际命中，因此未覆盖此路径。

## 实现合同

1. Enemy 生命周期及死亡事实不变；先将已验证的战斗结果提交到会话内存，失败保存不重建/复活敌人。
2. 复用现有单写者检查点机制（一个 in-flight + 一个可合并 pending，不创建另一种存档实现）。
   Daily 最多每 250 ms 请求完整不可变 Profile 检查点，空闲帧不复制整个 Profile。
3. 弹药/磨损、玩家伤害、敌人 HP/死亡以及位置来自同一份 Profile；工作线程不读取 Runtime。
4. 退出、切换存档、Deploy、开始 Defense 和普通持久化事务在写入前排空/停止 Daily 写者。
   拒绝的库存/医疗等事务不得进入后台队列；旧检查点不能晚于新事务写回。
5. 保存失败或后台持续落后 1 秒，停止推进战斗并显示可点击重试；不静默丢弃失败检查点。
   正常退出必须等待最新状态成功写入；异常终止只能恢复最近完整检查点（通常不超过一个批次，
   加上正在进行的存储时间）。这是明确的持久化策略变更，不称作纯行为保持重构。
6. F9 显示 Daily 检查点复制/序列化/提交/落后及代次，以区分主线程和后台耗时。

- Windows Debug 完整构建、全量 CTest、精确提交 Windows/Ubuntu CI；开发者不启动游戏。
- 用户最后在基地外围连续命中/击杀、整理/换弹、退出重开检查状态；同时观察 F9。
- 回滚只撤销本片提交到 a709162，不降级或改写用户存档；不自动合并。

## 实际结果

### Before / After 调用链

- Before：`updateBaseWorld → 复制 Profile → 同步 HP/死亡 → commitProfileCandidate →
  SaveRepository.save → 全校验/JSON/回读/备份/原子替换`，全部发生在命中帧。
- After：`updateBaseWorld → EnemyLifecycle 结果 → 稳定 ID 的小型敌人参与者/位置 → 内存 dirty`；
  每 250 ms `request(不可变 Profile copy) → 既有单写者后台保存`。另去掉无变更帧的两次全档复制。
- `普通持久事务 / Deploy / 新档 / Continue / 切存储 → 排空并停止 Daily 写者 → 原事务保存`；
  `正常退出 → 最新 Profile 检查点 → flush 成功才退出`。Defense 使用原写者和自己的策略。
- `失败/落后保护 → 停止模拟/时钟 → 可点击重试最新状态`，绝不通过重新配置 Enemy roster 恢复。

### 改动边界

仅 Daily 的检查点策略、命中参与者更新、必要 Session/GameFlow 写序屏障、F9/失败重试 UI 与测试。
复用 BaseDefenseCheckpointWriter 的原实现，不再造保存框架；未合并 Runtime 职责。
受伤命令可能替换候选 Profile，因此重新查询 site 迭代器，避免沿用已失效引用。
敌人配置、帧顺序、导航/弹道、伤害、掉落、资源文件、Save DTO 和版本号均未改变。
